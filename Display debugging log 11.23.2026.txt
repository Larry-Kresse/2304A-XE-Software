It would seem that none of the key codes are accepted. Meaning, the comms here is a bit more complex than just sending individual keys
over RS-232. I wonder if numerical input is handled client-side, and then transmitted to the 2304A once the user has hit enter. 

Note that this is NOT how the default panel input works! Every key press is sent immediately back to the main processor by serial.
To enter a number on the panel display, you hit "Menu", "Enter", and use the up/down arrow keys to adjust the number. Each press of any 
key is sent followed by the keyup code of '@'.

The same codes do seem to be allowed by the remote panel. Sending 'E' (OPERATE) followed by '@' (KEYUP) results in the output state toggling.
But numerical entry is different for some reason, and we need to figure out why.

During the initial reverse engineering, we didn't really test number editing. We just did numerical input with no special conditions.
We assumed that the codes wouldn't change and the control panel is a dumb keyboard. But it does have a microcontroller. Whoever did the
architecture of this thing chose to put a microcontroller controlling the PSU, a microcontroller on the panel display, and a microcontroller
in the remote RS-232-connected display. The commands appear to be the same for the panel display, at least which ones we tested. So I suspect
that there's more complexity in this system than meets the eye.

A smart developer, hardware or software, designs a common system once and uses it everywhere. I'm gonna bet the folks at Keithley were smart. 
I'm gonna bet they tested the individual-button press UI, and found it too slow. They still cared about the user experience, after all. 
Having each number adjustment go back to the main micro, and then main micro sending the updated display to the display controller, would result
in a LOT of messages and a LOT of lag for adjusting a number. Remember, the arrow keys UI means adjusting a digit could take up to 5 presses if
the user was behaving optimally. Or 9 if they weren't.
